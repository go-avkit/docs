decode

decode

github.com/go-avkit/decode (v0.5.0) decodes H.264 and HEVC / H.265 (Main and Main 10, 4:2:0) to planar YUV and FLAC, MP3 and Opus to PCM, in pure Go with no cgo. Vorbis, MP2 and AAC are not decoded. H.264 is decoded by oops1/go.264 (BSD-2-Clause), pinned and forced onto its software path; HEVC by gen2brain/h265 v0.2.4 (MIT). decode is the avkit-facing layer around them and the place where claims are measured. It is the only module in this organisation that produces pictures or sound.

Using it 

r, _ := container.NewReader(file)
frames, err := decode.DecodeTrack(r, trackID, decode.Config{})
for _, f := range frames { // display order
    use(f.Y, f.Cb, f.Cr, f.YStride, f.CStride, f.Width, f.Height, f.PTS)
}
  • H.264 input: an avcC record (decode.NewAVCC) or a TrackConfig (decode.NewTrack) with length-prefixed samples, fed with DecodeSample and ended with Flush; or a raw Annex B stream (decode.New, DecodeAnnexB).
  • HEVC input: the same calls choose HEVC for a track whose sample entry is hvc1 or hev1; decode.NewHVCC takes an hvcC record, decode.NewHEVC takes in-band parameter sets, and DecodeAnnexB a raw .265 stream. Main 10 frames hold little-endian 16-bit samples.
  • Output: frames in display order, with planes, strides, size, chroma format, bit depth and PTS.

One picture 

id, _ := decode.FirstVideoTrack(r)
f, err := decode.PosterFrame(r, id, 12.5, decode.PosterConfig{})

PosterFrame (since decode v0.2.0) returns the picture with the greatest presentation time at or before t, the very bytes DecodeTrack returns for it, without decoding the whole track: decoding starts at the last sync sample at or before the picture’s sample and stops as soon as the picture is out. It takes H.264 (avc1, avc3) and HEVC (hvc1, hev1); another codec is ErrUnsupported. A negative or NaN t is ErrTime.

Edit lists

Since v0.5.0, DecodeTrack and PosterFrame apply an MP4 track’s edit list by default, as ffmpeg does: a picture presented before an edit’s media time, or at its end or after, is decoded but not returned, presentation times are shifted so the pictures of the edit start at 0 (or at the length of the empty edit that delays the track), and PosterFrame’s t is a presentation time. This is a change from v0.3.0 for a file whose edit list trims or delays the track. Config.IgnoreEditList (ffmpeg’s -ignore_editlist 1) returns every picture labelled with track time, as v0.3.0 did.

An edit list the package does not apply is refused with ErrEditList rather than guessed at (a media rate other than 1, an edit lasting to the end of the media, an empty edit after the first edit that shows media, a media time before the track). Matroska has no per-track video edit list, so the first picture’s time is now 0, as in ffmpeg. Known divergence: for a fragmented MP4 with a trimmed start, ffmpeg and decode return different pictures (21 against 19 on the fixture), because ffmpeg switches its edit list support off for a fragmented file and decode cannot tell the file is fragmented yet (go-avkit/decode#20).

Audio 

id, _ := decode.FirstAudioTrack(r)
pcm, err := decode.DecodeAudioTrack(r, id, decode.AudioConfig{})
for _, a := range pcm { // presentation order, trimmed as the container states
    use(a.Data, a.Format, a.SampleRate, a.Channels, a.Layout, a.PTS)
}

NewAudioTrack streams it with DecodeSample and Flush. Data is interleaved little-endian PCM (s16le, s32le or f32le). The start of the track is dropped as its container states it (edit list, Opus pre-skip).

  • FLAC: 4 to 24 bits, 1 to 8 channels; a 32-bit stream is refused with ErrAudioUnsupported.
  • MP3: MPEG-1, 2 and 2.5, mono and stereo. MP2 (Layer II) is not decoded and is refused with ErrAudioUnsupported.
  • Opus: mono and stereo (mapping family 0); more channels (for example 5.1) are refused with ErrAudioUnsupported. Opus is checked against the RFC 8251 conformance vectors, not against ffmpeg’s output sample for sample.
  • Vorbis is not decoded: the one pure-Go decoder tried failed the comparison with ffmpeg, and no decoder was written. AAC is not decoded yet.

How it was measured

Every picture’s MD5 is compared with ffmpeg’s -f framemd5, single thread.

  • ITU-T H.264.1 conformance suite (AVCv1): 81 streams tried, 73 give the same pictures as ffmpeg. 69 do with go.264 v1.12.0 as pinned; 4 more (MR2 to MR5_TANDBERG) only with the upstream fix oops1/go.264#2, which is not yet released. The other 8 are not claimed: 5 interlaced and 3 using FMO/ASO.
  • JCT-VC conformance suite HEVC_v1 (ITU-T H.265.1): 147 streams. 143 give the same pictures as ffmpeg. Three are decided by the suite’s own MD5 because ffmpeg disagrees with it and decode agrees with it (SAODBLK_A_MainConcept_4, SAODBLK_B_MainConcept_4, VPSSPSPPS_A_MainConcept_1). One, TSUNEQBD_A_MAIN10_Technicolor_2 (luma and chroma bit depths differ), is refused by decode and by ffmpeg. The bitstreams are not in the repository, so the conformance test runs only when pointed at them.
  • Streams and real files in the repository: 29 H.264 and 5 HEVC streams run in CI against ffmpeg’s MD5s; real MP4 and Matroska files (5 H.264, 7 HEVC) are recorded as hashes.

Limits

A stream is untrusted. Config.MaxFrameMBs (default 36864, a 4096x2304 picture) and MaxSampleBytes (default 64 MiB) are checked before anything sized by the stream is allocated. Bomb tests assert a refusal under a memory limit for both video codecs, and the parsers and sample decoders are fuzzed with a committed corpus. AudioConfig limits the channel count, the block size, a coded sample and the PCM a track may return. PosterFrame has bounds of its own in PosterConfig: MaxSamples (default 600) caps the samples decoded for one picture, past it the error is ErrPosterLimit, and MaxTrackSamples (default 1«20) refuses a longer sample list.

Speed

Not yet measured against ffmpeg, so nothing is claimed about it. It is tracked in go-avkit/decode#2.
